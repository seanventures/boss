# BOSS Community 1.0.0-rc.9 candidate

RC9 builds on the published RC8 candidate and preserves the RC6.2 changes and Command Center design refresh. This branch is being qualified; RC8 remains the published release until an RC9 tag and download are available.

## What changed

- **Review the task before starting it.** The [work agreement](WORK_AGREEMENT.md) shows the selected workflow, repository, prerequisites and recorded approval requirements. Confirmation binds that exact plan to the current account and project. A changed workflow requires another review. If a start response is lost, check the existing run before trying again.
- **Review the delivered revision.** The [result review](RESULT_REVIEW.md) brings the recorded revision, checks, cost evidence and human decision together. Accepting records your review of that exact snapshot. Requesting a revision creates a bounded proposal; starting it remains a separate action.
- **Reuse your accepted checks.** Save the current accepted result’s recorded criteria, edit an append-only revision, and copy a starting point for a fresh task. [Saved checks](ACCEPTANCE_CHECKS.md) carry provenance and grant no execution authority.
- **Return to the work that changed.** The [returning-work brief](RETURNING_TO_WORK.md) links a small number of recorded changes to their exact run. It stores only a scoped last-seen timestamp on this browser. Missing or stale history stays unknown.
- **Inspect a diagnostic before saving it.** A run's [local diagnostic download](FEEDBACK_LOOP.md) uses the existing permission and redaction boundary. Inspect and edit the preview before saving the exact text. It does not automatically send the report.
- **Keep connection tests attributable.** A candidate API key stays separate from working connection material until a priced call succeeds. Connection proofs now commit a reservation, job/model lease and receipt before contact. Uncertain outcomes remain held for reconciliation. [Model connections](MODEL_CONNECTIONS.md) explains supported CLI-session setup and the limits of supplied subscription credentials.
- **Keep worker authority through acknowledgment.** Heartbeats continue through bounded completion, failure and deferred-result acknowledgment. A delayed response no longer ends renewal before the worker reports its outcome.
- **Admit retries before provider writes.** Retry admission no longer refreshes a GitHub branch before the new work has authority. Portable retry lookup uses canonical job authority instead of historical run metadata.
- **Recover cleanup after restart.** A bounded durable-ledger scan can release an exact pending database/role record after both resources are proven absent. It does not grant new deletion authority. See [build isolation](SANDBOX.md).
- **Require a working IPv6 fence.** When IPv6 is usable, missing or failed IPv6 rules keep build execution held. A positive kernel-disabled result is the only supported reason to skip those rules.
- **Reject oversized public requests early.** SAML/SCIM proxy requests use a capped stream reader; an absent or understated length cannot make the proxy read the complete oversized request first. Existing protocol and response-stream behavior is retained.

The first-use website and manual focus on one accountable software change, with actual installed-console screenshots and explicit setup requirements. The separate website release preserves its existing signup and mail service; local website preparation is not hosted deployment.

## Install and upgrade

Until RC9 is published, use the [published RC8 instructions](RELEASE_NOTES_v1.0-rc8.md). A source checkout must record the exact selected commit, and an existing install should take a complete protected backup before upgrading. Changing the checkout back does not undo database migrations.

Protect backup archives as credentials. Do not attach an archive, your `.env`, session cookies or model credentials to a bug report.

## Qualification

The [RC9 validation record](RC9_VALIDATION.md) distinguishes source checks, installed images, live provider results, supported hosts and human first use. The release changes do not establish voluntary repeat use or a useful live-provider outcome. The original top-30 recommendations and subsequent findings remain tracked; source publication does not close every qualification item.

Budget reservations authorize an estimated call; they do not cap a provider's final invoice. Reconcile uncertain provider outcomes before retrying, and reconcile later external effects before resuming workers from an older restored snapshot. A stored credential or a readable result is not evidence that the complete provider journey has passed.

This is incremental Community release work. It retains the published contributor history; full private-source export synchronization remains separate. Runtime build contexts exclude application tests and scratch probes. Release downloads contain source and checksums, not prebuilt container images.
