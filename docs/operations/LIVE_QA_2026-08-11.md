## Ranked findings

### P0 — ProviderOps / System Configuration dead on live

Mission Control SSR marks the ProviderOps feed `apiReachable=false` on **every** area with:

> Provider catalog / accounts / Resources / ChangeSets / Resource receipts / Worker pools / Scale plans — **HTTP 404**

Live OpenAPI **does not register** the routes the web client calls (`/v1/providers`, `/v1/provider-definitions`, `/v1/resources`, `/v1/resource-receipts`, `/v1/worker-pools`, `/v1/scale-plans`, ChangeSets). Present instead: `/v1/provider-health`, limited `/v1/finops/*`, `/v1/infra/resources*`.

**Impact:** System Configuration (and any global ProviderOps fan-out on the console shell) is non-functional while the shell still pays the cost of those calls on every SSR.

**Root cause (confirmed in code + live):** `BOSS_EDITION=community`.  
`test_edition_routers.py` classifies `/v1/providers` and `/v1/provider-definitions` as **enterprise** and asserts community omits them. Live OpenAPI matches that. The **web still SSR-fetches ProviderOps on every area**, so community dogfood shows a permanent partial-failure banner (`apiReachable=false`) — the same “half a workflow / UI looks broken” class already called out for delivery targets in those tests.

**Fix direction:** either promote ProviderOps reads to community (if dogfood needs System Configuration), or make the console edition-aware and skip ProviderOps fan-out when routes are not mounted (fail soft, not 404 noise on all 28 areas).
