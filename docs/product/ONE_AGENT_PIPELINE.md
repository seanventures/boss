# One agent pipeline

Plane BOSSAPP-759. Operator decisions, 2026-10-23:

- "Metatron is just the CLI that interacts with the core BOSS agents… if two have different code path for AI agents then we have to make duplicate fixes every time — avoid that."
- "Why do we even have the captain autopilot? Retire it. Put its functionality into the BOSS agent. There must be ONE agent pipeline, and all agents go through it. Some agents may have extra skills (customised by the user), but when BOSS ships, all agent communication goes through the same code path: console, API, CLI, and agent-to-agent too."
- "ALL BOSS default (shipped) agents have the SAME expertise and the SAME full action and tool access through the one pipeline. They differ only by skills and MCP servers an operator assigns in the console, or when a user customizes an agent."

## The pipeline

| Part | Where | What it does |
|---|---|---|
| The turn | `apps/api/app/main.py:agent_turn` | Every conversational HTTP surface sends a turn here. It handles rate limiting, the project check and error wording, then calls `AgentService.chat` |
| The conversation | `engine/boss_engine/services/agent_service.py:AgentService.chat` | Thread model (`agent_threads`, `agent_messages`), signed acts, the pending plan |
| The decision | `engine/boss_engine/services/intent_router.py:IntentRouter.route_turn` → `agent_decision.decide` | A model picks the turn's action from the action catalogue. Words are never a rule |
| A domain agent's turn | `agent_service.py:AgentService.decide` → `IntentRouter.decide_among` → `agent_decision.decide` | The same decision, for an agent whose actions are its domain's (an alert, a reply, an issue, a root cause). The caller passes the candidates, the record and its pattern guesses as hints. The turn is kept on the record's own thread (surface `agent`, `external_ref` = the record), whose earlier turns are the decision's history. What the chosen action does stays the caller's, under its own governance |
| A structured decision | the same `AgentService.decide`, with `Choice(arguments=…)`, `check`, `read`, `brief`, `envelope` | For a decision that is more than a choice. Each choice may carry an argument schema, and the decision returns the chosen action's arguments validated (`AgentDecision.arguments`). `check(answer, corpus)` is the caller's check against what the agent was shown (the context, the hints and every read result); a refused answer is asked once more with the refusal, and refused twice nothing is decided (`refused` says why). `read` (`ReadPhase`) is a bounded read phase: read tools the agent may call before it answers, capped in turns and model cost by the caller. `brief` is the caller's own rules, after the decision's. `envelope` runs the call inside the caller's spend envelope (below) |
| The answer | `engine/boss_engine/agent/engine_agent.py:EngineAgent`, with `tools.build_discuss_read_registry` | The tool loop. Reads run, and writes run or are offered according to `ToolSpec.self_executable` |
| The streaming answer | `agent_service.py:AgentService.answer_stream` → `engine_agent.py:stream_answer` | A role-addressed turn whose answer streams as the model writes it (`stream_text_response`; an adapter that cannot stream answers whole). It runs only in `discuss`: no tools, nothing written. It can run under a caller's `SpendEnvelope` |
| A caller's spend envelope | `agent_decision.SpendEnvelope`, e.g. `conversation_spend.ConversationCallSpend` | The model attempt a caller already governs: one pinned provider, a reservation and model lease held across the live stream, a settled receipt and, for a conversation, the floor claim checked between chunks. The pipeline's call (the streaming answer, or a decision) runs inside it in place of the pipeline's own governance. An envelope admits one attempt, so a decision under it is never asked twice, and its failures (a reconciliation it must hold, a stopped stream) are raised for its owner to settle. The envelope makes no model call of its own |
| The press | `apps/api/app/main.py:agent_action` (`POST /v1/engine/agent/action`) | Runs exactly the offer the person accepted, with no model in between. It checks the tool's permission, the identity gate and consent, and records the outcome in the transcript |

Governance is the same for every caller: permission and identity gate, consent (`propose_action` and `operator_only`), step-up, budget, receipts and Passport ceilings.

### Workers, and where the boundary is

A worker calls a model to produce an artifact, such as code, a PRD, a review, an edit plan or a drafted workflow. It doesn't choose what BOSS does next. Workers stay outside the pipeline, and so do the coding engines inside a build step (`code_agent.py`, the CLI harnesses), panel seats and PRD synthesis (`meeting_service.py`), the PR reviewers, `meeting_actions.py`, `prd_decomposition.py`, `video_planner.py`, `workflow_drafting.py`, `typed_decisions.py` (it answers a workflow author's own question), the read-only pre-check, `sre_ask.py` (it plans a query and never executes one), the factory plan artifact and `agent_loop.py`, which carries out a workflow agent step's instruction with only its agent's granted skills (each call re-checked by `SkillRuntimeService.invoke`, tier-3 skills still suspending the run). The boundary is choosing a BOSS action. Any module that picks which BOSS action to take, offer or skip belongs in the pipeline.

`engine/tests/test_one_agent_pipeline.py` enforces this. Any module that imports the decision model, builds or calls the router, calls a model or runs its own tool loop must appear in its `ALLOWED` list with a reason. An entry not moved yet would be marked `MIGRATE` there; none is left. The list can only shrink: an entry that stops deciding on its own fails the test until someone removes it. Metatron's router, the captain service, the captain tools, `focused_agents.py` and `metatron_command.py` may never decide on their own. The conversation's envelope (`conversation_spend.py`) may never call a model again, and every talk, plan and room seat must speak through `answer_stream`.

### Intentional differences

- **Typed captain commands skip the model.** `/overwatch` is the person pressing the agent's `captain_overwatch` action, like a console button. A press is never re-decided.
- **The overwatch playbook stays deterministic.** Inside `captain_overwatch` and `captain_drive`, `validate_move`, the budget and duplicate checks and "decisions and dead letters never apply" still run as code. That logic is how the tool does its job. It doesn't choose what BOSS does next: the agent or the person chooses whether to run the tool.

## Same base for every shipped agent

Every shipped agent holds the same baseline skills (`agent_baseline.BASELINE_SKILLS`): `boss.fundamentals`, `repo.read`, `boss.propose_fix`, `knowledge.read` and `knowledge.propose`. Every agent also gets the same chat registry, whoever is asked. The role changes the lens and the history, not the reach.

- **Removed:** the six-role `kg_propose_fact` grant (`PROPOSE_FACT_ROLES` and the `knowledge.propose` entries in six role specs). `knowledge.propose` is in the baseline. What it writes is always `inferred`, the same governance for every agent.
- **Kept:** each role's specialist skills in its spec's `allowed_skills`. These are data that `sync_role_skills` writes into `role_skills`, and an operator can see and change them in the console like any other grant. Governance is unchanged: approvals, step-up, budget, receipts, Passport ceilings and consent.
- **Enforced:** `engine/tests/test_every_shipped_agent_has_the_same_base.py`. No role list and no comparison against a shipped role key may appear in the pipeline's code. The base is one constant, not a function of the role. No role spec may forbid a baseline skill. The chat registry takes no role.

## The migration, in risk order

1. Incident verdict (`investigation.py`): **moved** (`AgentService.decide`).
2. GitHub issue triage and inbox replies (`github_triage_agent.py`, `comms.py`): **moved**.
3. Alert triage and flap tuning (`app_alerts.py`): **moved**, keyed to the incident.
4. Agent-to-agent talk, plan and room (`agent_converse.py`, `conversation_spend.py`): **moved** (`answer_stream` for every seat, `decide` for the start card, both inside the conversation's envelope). See "Moved last".
5. Focused agents (`focused_agents.py`): **moved** (`AgentService.decide` over the validated moves, not `chat`; see the table).
6. Step recovery and the workflow agent step (`step_recovery.py`, `agent_steps.py`, `agent_loop.py`): the agent step's choice of agent is **moved**, and its loop is a worker. Step recovery is **moved** (a structured decision). See "Moved last".

Each step moves its module out of `MIGRATE` in `test_one_agent_pipeline.py` and runs the battle set's scenarios for that surface. A moved module is listed in that test's `MIGRATED`, which checks that it calls `AgentService.decide` and nothing on the decision signs. `SPEAKS_THROUGH_THE_PIPELINE` checks that the conversation's seats call `answer_stream`, and `ENVELOPES` that the envelope makes no model call.

## Moved last

These two needed a change to the pipeline itself, not only to the entry point. Both design notes are built as written, except where this section says otherwise.

### Agent-to-agent talk, plan and room

**What it needed.** A talk, a plan and a room are conversations between a person and one to five seated agents. Each seat's reply is one model call, streamed token by token to the console, under the conversation's own spend envelope (`ConversationCallSpend`): one pinned provider attempt, a reservation and a model lease held across the live stream, a settled receipt, and the floor claim that keeps two streams from speaking at once. The pipeline's turn answered in one piece and governed its own calls.

**What was built.**

1. The pipeline's answer has a streaming form: `engine_agent.stream_answer` yields the words through the adapter's `stream_text_response` (an adapter that cannot stream answers whole). It is lazy, so the provider is contacted at the first `next()`, inside the envelope's single-attempt and deadline scope, and its `close()` is the provider's own close (a stopped stream ends the CLI process; a close that fails is the envelope's `producer_failed`).
2. `AgentService.answer_stream(role=<seat>, mode="discuss", envelope=…)` is the streaming answer turn. `ConversationCallSpend.stream` now takes the pipeline's `produce` and calls no model itself: it pins, admits, leases, heartbeats, enforces the deadline and byte limits, and settles, as before. `agent_converse._envelope` wraps it as the turn's `SpendEnvelope`.
3. Every talk, plan and room seat speaks through `answer_stream`. Round two, one agent answering another, is the same turn with the earlier seat's reply in its prompt. The SSE events (`turn_start`, `token`, `turn_end`, `error`, `done`) are unchanged, so the console and Metatron, which read the same `/v1/conversations` stream, see what they saw before.
4. The plan's start card is `AgentService.decide` over the catalogue's workflows, by the lead seat in its own voice (its composed persona is the decision's `brief`), with the conversation and what it is about as the record. Each workflow is a choice whose argument schema is the card's draft: message, title, directive, inputs, acceptance criteria, why, and who runs each step. `validate_proposal` is the check. A card changes nothing until the operator presses it, so every workflow is a choice that does not act (`acts=False`), and the confidence bar does not hold the card back.

**Where it differs from the design note.**

- **A seat's turn does not go through `route_turn`.** An addressed seat has one thing to do, which is to answer. There is nothing for `route_turn` to choose, so a decision call would be a second paid call that changes nothing. The seat's turn is the pipeline's streaming answer, and the one thing a conversation does choose (the start card) is the pipeline's decision. The turns stay on the conversation's own thread (`agent_conversation_turns`, and the acts whose thread is the conversation), not in `agent_threads`.
- **The card is one attempt.** It runs inside the turn's envelope, which admits one provider attempt, so an answer that `validate_proposal` refuses is not asked again. The turn fails with the reason, as a malformed plan did before. The card is still one governed, settled call with one receipt, not two.
- **The room's summary stays a worker's draft.** It writes the outcome, the decisions with who was for and against, and the next actions. Its start items are checked by `validate_proposal` and offered for a person to press, as before.
- **The decision's contract is the pipeline's.** The card is answered as `{"action": <workflow_key>, "arguments": {…}}`. A model that puts the arguments beside `action` instead of under `arguments` has still given them.

**Tests.** `test_a_talk_streams_as_the_model_writes`, `test_a_talk_never_claims_an_action`, `test_talking_with_agents`, `test_conversation_stream_intent` (receipts, leases, reconciliation, replay, the floor and the deadline), `test_a_conversation_is_part_of_the_work` and the pipeline test's `test_a_seat_speaks_through_the_pipelines_streaming_answer_inside_the_callers_envelope` and `test_a_decision_under_an_envelope_is_one_attempt_and_never_asked_twice`.

### Step recovery

**What it needed.** A failed step's recovery agent runs unattended inside a build, and its decision is more than a choice. The model (1) reads more evidence with BOSS's read tools for up to `MAX_TURNS` turns, inside the step's recovery budget; (2) answers with the action and that action's arguments: a precise note for `fix_app`, the projects to take down for `clean_and_retry`, a `boss_fix` with an area and reasons for `wait_for_boss` and `fix_boss`, one question and what happens after for `ask_person`, and a backoff for `retry`; and (3) is checked by `validate` before anything runs. The check covers the step kind's allowed actions, the same action for the same cause twice, projects that are not this app's own, and cited evidence that appears nowhere in what the agent was shown. A refused answer gets one re-ask.

**What was built.**

1. `Choice` has an optional argument schema (`arguments`), and `agent_decision.decide` has an optional `check` (the caller's validator, which returns the refusal reason) with one re-ask on refusal. The JSON contract gains `"arguments": {…}` and `"evidence": […]` for the chosen action.
2. `decide` has an optional read phase (`ReadPhase`: the tools, their runner, and the caller's caps in turns and model cost). Its tool results join the corpus that `check` cites against. The loop is the one step recovery ran: tools on every turn but the last, "answer now" on the last, the refusal re-asked once in the same conversation, and a turn the per-minute budget defers reported, never waited for.
3. `step_recovery.decide` calls `ask_model`, which is `AgentService.decide(role=<the step's agent>, external_ref="step:<run>:<step>")`. Its inputs are `ACTIONS` narrowed to `KINDS[kind]` as the choices, the evidence pack as the context, the coded triage as a hint, `SYSTEM_PROMPT` as the brief, the fundamentals reads as the read phase and `validate` as the check. Its budget window, `no_model_ask`, `unsure_ask` and execution stay as they are.

**Where it differs from the design note.**

- **The read phase is the caller's reads.** The recovery agent's tools are the pre-check agent's fundamentals reads (`workflow_precheck_agent.read_tools`, taken from `build_discuss_read_registry`), as before. `ReadPhase` takes whatever read tools the caller holds, so it is not tied to one registry.
- **The model is the one the caller's route chose.** `step_recovery.routed_adapter` still asks the router for tier Balanced and governs every turn as `model.step_recovery` under `recovery:<run>:<step>`, and hands that model to the decision. The receipts and the budget are the same as before.
- **The confidence bar stays the caller's.** The decision runs with `min_confidence=0`, and `step_recovery.decide` turns an unsure answer into `unsure_ask`, which carries the suggested action and its arguments for the person. That is the design note's "`unsure_ask` stays as it is".
- **A malformed argument is refused.** One whose type is wrong is refused and re-asked, such as `projects` that is not a list or a `backoff_seconds` that is not a number. A number written as a string is still accepted. Before, a non-numeric backoff became 60 seconds.

**Tests.** `test_a_failed_step_is_recovered_by_its_agent`, the recovery API tests (`test_a_failed_build_recovers_on_its_own`, `test_a_failed_deploy_recovers_on_its_own`, `test_a_deploy_that_fails_for_the_app_is_fixed_and_redeployed`), the self-fix and findings tests, and the pipeline test's `test_a_structured_decision_reads_first_checks_its_evidence_and_asks_once_more`. The battle set's `step_recovery` scenarios were run with scripted models (one that follows the triage, one whose first answer cites evidence it was never shown, one whose first answer is an action outside the step's set, and no model). There are 172 runs, and their recorded decisions are identical before and after the move.
